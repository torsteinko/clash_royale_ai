# GPU simulation — plan and milestones

Goal: a **batched, tensor-based reimplementation** of the crforge battle engine
that runs on the RTX 5070 Ti, validated as *equivalent* against the Java
reference (agreed standard: validated-equivalent, not bit-identical).

End state: 1 024+ concurrent battles as tensor ops, 50 000+ steps/s, driven by
the same training stack (SB3 VecEnv-compatible), with league self-play.

## Milestones

- [x] **M0 — Data frozen.** L1 = 0 known mismatches vs current (noff 2026-09)
  except semantics-watch (xbow) + logged reference quirks. Patched data:
  `fidelity/patched/` (generated by `fidelity/apply_fixes.py`).
- [ ] **M1 — Batched core skeleton** (this: `gpusim/`). Tensor state, tick loop,
  elixir economy, deployment with formation offsets, level scaling table,
  basic movement. CPU tests green.
- [ ] **M2 — Core mechanics.** Bridge waypoint pathing, targeting priorities
  (air/ground/buildings-only), melee/ranged combat with hit speeds, king-tower
  activation, projectiles, unit collision occupancy.
- [ ] **M3 — Full rules.** Spells (radius, falloff, tower damage %), deploy-time
  rules and placement zones, overtime + tiebreak, win conditions, card cycle.
- [ ] **M4 — Differential harness.** Fixed scenarios + recorded replays run in
  both sims; tower HP / elixir / survival / timings diffed within tolerances.
  This is the acceptance gate for "validated-equivalent".
- [ ] **M5 — Throughput + integration.** 50k+ steps/s on the 5070 Ti; SB3
  VecEnv adapter (`gpusim/vecenv.py`); train-loop parity check vs Java stack.
- [ ] **M6 — Scale.** League self-play, BC warm-start from replays.

## Architecture decisions

- **Framework: PyTorch**, device-agnostic (dev/test on CPU, train on CUDA).
  Rationale: already in the stack (SB3), stable on the 5070 Ti, no extra
  toolchain. Revisit Warp/custom kernels only if throughput demands it (M5).
- **State: SoA tensors** `(B, MAX_slots)` — all envs tick in lockstep, no
  per-env Python branching. Fixed caps per env (units/projectiles), active
  masks. Overflow policy: assert in tests, log+drop oldest in training.
- **Determinism:** pure functions of (state, actions, tick index); no random
  in core except explicitly seeded deploy jitter (off in eval).
- **Source of truth:** Java crforge stays the reference implementation; every
  mechanic ported 1:1, verified by M4 harness. Mechanics are never "simplified";
  if a mechanic cannot be ported yet it must be *flagged as TODO-divergence* in
  `gpusim/DIVERGENCES.md` and excluded from training configs until ported.

## Repo layout

- `gpusim/cards.py` — card/unit tables from the patched data (tensors)
- `gpusim/env.py` — `BatchedCRSim`: reset/step, deployment, tick loop
- `gpusim/tests/` — CPU tests (the spec in executable form)
- `gpusim/vecenv.py` — M5 SB3 adapter
- `gpusim/DIVERGENCES.md` — tracked deviations from the Java sim
